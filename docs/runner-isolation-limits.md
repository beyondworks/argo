# 러너별 격리 한계 — 권한 게이트가 어디까지 닿는가

작성 2026-07-27. 계기: 능력이 전부 꺼진 크루가 워크스페이스 직속 `capabilities.json`을 고쳐
다음 턴에 셸·바이패스를 획득하는 자가 승격을 격리 환경에서 재현하고 게이트를 고치면서, **그 수정이
어느 러너까지 실제로 적용되는지**를 같이 적어 둘 필요가 생겼다.

## 결론 한 줄

권한 게이트(`src/permission-gate.mjs`)는 **SDK 러너의 도구 호출에만** 걸린다. 외부 CLI 러너는
프로세스 단위 샌드박스라 게이트를 지나지 않고, 워크스페이스 안은 쓰기가 열려 있다.

| 러너 | 경로 | 제어 파일 쓰기 | 근거 |
|---|---|---|---|
| claude / glm / kimi / openrouter — shell OFF | SDK `query({canUseTool})` | **하드 차단** | 격리 재현·회귀 테스트 실측 |
| 〃 — shell ON | 같은 게이트 + Bash 리터럴 스캔 | **1차 방어만** (아래 참고) | 실측 |
| codex (맥·리눅스) | `codex exec --sandbox workspace-write`, cwd=워크스페이스 | 막지 못함 | 코드(`runners.mjs`) — 라이브 미검증 |
| codex (윈도우, 2026-08-06~) | `codex exec --dangerously-bypass-approvals-and-sandbox` | 막지 못함 + **OS 샌드박스 자체가 없음** | 윈도우 codex는 샌드박스 기전 부재로 workspace-write가 read-only로 떨어져 쓰기 전멸(신고 4건 전부 윈도우 + openai/codex#6374). 전권 원칙에 따라 우회 — 근거·되돌림 조건은 `src/runners/codex.mjs` `codexSandboxModeArgs` 주석 |
| gemini | `--approval-mode auto_edit` | 막지 못함 | 코드 — 라이브 미검증 |
| antigravity | `--mode accept-edits` (셸 OFF면 `--sandbox`) | 막지 못함 | 코드 — 라이브 미검증 |

"하드 차단"은 **도구 단위 차단(Write/Edit/Read/Grep/Glob/MCP/미분류 도구)** 에 한한 말이다. `shell` 능력을
켜면 Bash가 열리고, 게이트가 할 수 있는 것은 명령 문자열에 금고 파일명이 리터럴로 들어간 순진한 시도를
잡는 1차 방어뿐이다(`BASH_GUARDED`) — 변수·상대경로 조합으로는 우회된다. 이는 `APP_ROOT`·`~/.argo`에
적용해 온 방어와 같은 수준이고, 같은 한계를 갖는다. **셸 능력을 켜는 것은 그 회사 안에서 전권 위임에
준한다**고 읽는 것이 정확하다.

## 왜 외부 CLI에서는 막을 수 없나

`externalExec`는 워크스페이스를 `cwd`로 주고 codex를 `--sandbox workspace-write`로 띄운다
(`src/runners.mjs`). 이 모드의 정의가 "cwd 안은 쓰기 허용"이므로, 워크스페이스 직속에 있는
`capabilities.json`·`mcp.json`·`agents/*.md`도 그 허용 범위 안이다. 도구 단위로 가로챌 지점이 없다 —
SDK의 `canUseTool`에 해당하는 훅이 없고, 셸 실행이 도구와 분리되지 않는다.

`caps.fs`를 켜면 범위가 더 넓어진다: `writable_roots=[홈]`이 되는데, 워크스페이스 루트(`ARGO_ROOT`,
데스크톱 기본은 홈 아래)가 그 안에 들어간다. 즉 fs를 켠 codex 크루에게 워크스페이스는 언제나 쓰기 가능하다.

현재 방어는 시스템 프롬프트의 금지 지시(`commonDirectives`) 한 겹이다. **이것은 계약이지 보장이 아니다**
— 프롬프트는 힌트고 코드가 보장한다는 원칙에서 보면, 외부 CLI 러너 경로는 아직 보장이 없는 상태다.

## 지금 이 상태를 수용하는 근거

- 자가 승격의 실질 이득은 **셸·바이패스 획득**인데, codex 러너는 애초에 셸이 프로세스 안에서 열려 있다
  (능력으로 분리 차단이 안 된다 — `codexSandboxArgs` 주석의 기존 결론). 즉 codex 경로에서 승격은
  "이미 가진 것"에 가깝고, 순증분은 바이패스(결재 자동 승인)다.
- 사용자 본인 기기에서 사장이 명시적으로 연결한 러너 뒤에서 도는 구조다.

그래도 **바이패스 획득은 결재 모델을 무력화하므로 잔여 위험으로 남는다.** 수용은 "무해하다"는 뜻이 아니라
"지금 고칠 수단이 없다"는 뜻이다.

## 고치려면 (미구현 — 설계안)

1. **턴 경계 변조 감지**: 턴 시작 시 제어 파일 해시를 기록하고 종료 시 대조해, 크루 턴 중 바뀌었으면
   되돌리고 사장에게 알린다. 러너 종류와 무관하게 동작하는 유일한 방어다.
2. **제어 파일을 워크스페이스 밖으로**: cwd 밖(예: `WS_ROOT/.control/<wsId>/`)에 두면 `workspace-write`
   범위에서 빠진다. 다만 동기화·복구·백업 경로 전체가 영향을 받는 구조 변경이라 비용이 크다.

1번이 비용 대비 효과가 낫다. 별도 작업으로 다룬다.

## 러너와 무관하게 남은 잔여 위험 (분리 검수 2026-07-27에서 확인)

게이트를 고쳐도 남는 것들이다. 자가 승격(능력 불리언 조작)은 아니지만, **결재를 거치지 않는 지속적
지시 주입**이라는 점에서 같은 계열이다. 지금은 수용하고 여기 적어 둔다.

- **`skills/*.md`** — `loadSkills`가 본문 그대로 전 크루의 시스템 프롬프트에 붙인다(`chat.mjs`). 크루가
  자기 스킬을 남기는 것은 설계된 기능(스캐폴드 README가 안내한다)이라 막지 않았지만, 결과적으로 결재
  없는 지속 지시 주입 경로다. 좁히려면 스킬을 작성 크루 범위로 한정하는 설계가 필요하다.
- **`inbox/`** — 게이트웨이 워처가 이 폴더의 파일을 발견하면 프롬프트에 "사장이 inbox에 파일을 넣었다"고
  못박고 턴을 띄운다(`gateway.mjs`). 크루가 여기 파일을 쓰면 사장 발신으로 위장한 턴을 자가 기동할 수
  있다(워처가 도는 구성에서만). 워처 쪽에서 작성 주체를 구분하는 것이 정식 대응이다.
- **`bypass` + 호스트 MCP 임포트** — `bypass`가 켜져 있으면 `request_tool_install`이 결재 없이 실행되고
  `source='host'`는 사용자의 `~/.claude.json` 서버 정의를 env까지 들여온다(`chat.mjs`·`market.mjs`).
  게이트는 이제 외부 MCP 도구의 경로 인자를 검사하지만, 파일 경로를 인자로 받지 않는 실행형 MCP는
  검사 대상이 없다. `source='host'`를 bypass 자동 승인에서 제외하는 것이 검토 대상이다.
