# 장시간 작업 큐 — 설계서 (2026-07-26 초안, 승인 대기)

> 목적: **크루가 몇 시간 걸리는 일을 걸어두고, 사장은 기다리지 않고, 끝나면 결과가 도착한다.**
> 계기: 브라우저 자동화(수 분~수십 분) 작업이 "백그라운드로 던지면 출력이 사라진다"는 갭
> (2026-07-26 실측 확인). 전경 실행은 Bash 상한 10분이 한계라 그 이상은 구조가 필요하다.

## 왜 지금 가능한가 — 이미 있는 것

| 조각 | 위치 | 재사용 방식 |
|---|---|---|
| 파일 기반 큐 + 원자적 적재 | `gateway.mjs` `enqueueJob` / `queueDir` | 큐 키만 새로(`jobs`) |
| 드레인 워커(1초 폴·동시 상한·재기동 복구) | `gateway.mjs` `startQueueWorker` | 그대로 |
| 워커 등록/해제 관리 | 게이트웨이 매니저의 `drainers` | 항목 추가 |
| 장시간 실행 가능한 턴 | `chat()` — 워커 경로엔 HTTP 5분 상한이 없다 | 그대로 |
| 결과를 대화에 남기기 | `appendTurn` | 그대로 |
| 메신저 통지 | `emitNotify`(루틴이 쓰는 경로) | 그대로 |
| 진행 상황 UI | `TasksDock` + `/api/companies/[ws]/tasks` | 대기·예약 항목 추가 |
| 중단 | `turn-abort.mjs` `registerTurn` | 취소에 연결 |

**핵심 통찰**: 긴 작업은 "여러 턴"이 아니라 **한 번의 긴 `chat()` 호출**이다(도구 호출을 수십 번 하며
스스로 진행). 워커 경로에는 턴 타임아웃이 없어 몇 시간도 돈다. 없는 것은 **대화를 막지 않고 시작하는 방법**과
**끝났을 때 결과를 배달하는 경로**뿐이다.

## 설계

### 잡 스키마 (`.gw-queue-jobs/<ts>-<rand>.json`)
```
{ id, slug, title, prompt, createdAt, dev, startedAt?, tries }
```
`dev` = 적재 기기(기존 큐 관례 — 그 기기의 워커만 실행). `tries` = 재시도 횟수(아래 중복 방지).

### 실행
워커 handler가 `chat(wsId, slug, prompt, null, { source: 'job' })` 호출 → 완료 시
`appendTurn`(대화에 결과) + `appendEvent`(활동) + `emitNotify`(텔레그램/슬랙 통지).
실패는 같은 3곳에 실패로 기록하고 잡 파일을 지운다(무한 재시도 금지).

### 크루 도구 `start_long_task(title, prompt, agentSlug?)`
"지금 시작하되 이 턴을 막지 않는다". 적재 후 `"걸어뒀다"`만 보고하고 턴을 끝낸다.
`schedule_task`(시각 예약)와 구분: **이건 즉시 시작·1회·장시간**.

### 중복 실행 방지 (게이트웨이 큐와 다른 점 — 중요)
게이트웨이 큐는 "크래시 시 재처리"가 안전하다(메시지 재응답은 무해). 잡은 **발송·구매 같은 부작용을
포함할 수 있어** 무제한 재시도가 위험하다. 그래서:
- 시작 시 `startedAt`·`tries+1`을 잡 파일에 기록(원자적 갱신)
- 재기동 시 `tries >= 1`인 잡은 **자동 재실행하지 않고** 활동에 "중단된 작업"으로 남기고 사장이 재시작을 결정
- 이 규칙은 "발송류는 사람이 잠근다" 원칙과 같은 방향

### 동시 상한·비용
잡 전용 상한 1(게이트웨이의 2와 별도) — 장시간 작업이 메신저 응답을 굶기지 않게 큐를 분리하고,
월 지출 한도는 `chat()`이 이미 검사한다(초과 시 잡은 실패로 기록되고 안내가 남는다).

### 가시성·제어
- `TasksDock`: 진행 중 잡을 턴과 함께 표시(경과 시간·제목), 대기 중 잡은 "대기" 배지
- 취소: 잡 파일 삭제(대기) 또는 `turn-abort` 호출(진행 중)
- 활동 화면: 시작·완료·실패·중단 이벤트

## 단계 (각 단계가 그 자체로 출하 가능)

| 단계 | 내용 | 검증 |
|---|---|---|
| **S1 최소 출하** | 큐 키·워커 등록·`start_long_task` 도구·완료 통지 | 격리 서버에서 10분 넘는 잡(sleep+파일 쓰기)이 대화·메신저에 결과를 남기는지 실측 |
| **S2 가시성** | TasksDock 대기·진행 표시, 취소 버튼 | 브라우저에서 대기→진행→완료 전이 눈으로 확인, 취소 시 실제 중단 |
| **S3 중간 보고** | 부분 결과 파일 기반 진행 알림(텔레그램 90초 알림과 동일 계약) | 장시간 잡에서 중간 알림 1회 도달 |

## 열린 질문 (구현 전 결정)

1. **리더 기기 규칙**: 잡은 적재 기기가 실행(기존 큐 관례)인가, 리더 기기가 실행인가? 노트북에서 걸고
   덮으면 멈춘다 vs VPS/상주가 이어받는다. **제안: 적재 기기 우선 + 24시간 내 미완이면 리더가 인수**(2단계).
2. **결재 경계**: 잡 안에서 발송이 필요하면? **제안: 지금과 동일 — 잡 안에서도 결재를 올리고 대기.
   승인되면 후속 턴으로 이어짐**(잡은 결재를 기다리며 살아 있지 않고, 결재 후속 턴이 잇는다).
3. **상한**: 한 회사당 동시 1개가 맞나, 대기 큐 길이 상한은? **제안: 동시 1 · 대기 10.**

## 결론

S1은 새 인프라가 거의 없다 — 큐 키 하나, 워커 등록 한 줄, 도구 하나, 통지 재사용.
"10분 넘는 작업"이라는 유일한 남은 패리티 갭을 닫고, 네이티브보다 나은 지점(기기를 꺼도 결과가 배달됨)까지
간다. **승인되면 S1부터 착수한다.**
