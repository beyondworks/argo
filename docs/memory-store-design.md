# 회사 기억 저장소 설계 — sqlite 캐시 + git blob 정본화

> 작성 2026-07-26. 유건 제안(① git blob을 정본으로 두어 버전 관리 ② sqlite 캐시로 10만 파일 규모 대응)에 대한 설계.
> 코드 변경 0줄 — 이 문서는 승인 대상이다. North Star = "폴더 단위 기억으로 일 시키는 SaaS".

## 1. 왜 (실측 근거)

### 1-1. 정확성 — 갱신 시각을 파일 밖에서 복원하고 있다

`_index.md`가 크루의 기억 진입점인데(`src/chat.mjs` 시스템 프롬프트 "vault/_index.md를 먼저 읽고"),
2026-07-26 이전까지 이 인덱스는 모든 문서를 **파일명 역순**으로만 정렬했다. 일지는 파일명이
`YYYY-MM-DD-`로 시작해 결과적으로 최신순이었으나, 주제 노트는 파일명이 주제 슬러그라 **순서에 시간
정보가 0**이었다. 실측: 같은 주제 3벌(3월·5월·7월)에서 3월 절차가 맨 위였다.

`836d26d`에서 지혈했지만, 그 과정에서 드러난 건 **시각의 근거가 없다**는 구조적 사실이다.

| 근거 | 문제 |
|---|---|
| frontmatter `updated:` | `saveNote()`만 찍는다. 크루는 노트 저장 도구가 없어 SDK 기본 `Write`로 직접 쓰므로 **크루 노트엔 없다** |
| 파일 mtime | 역링크 append가 내용 갱신 없이 올린다(`836d26d`에서 `writeKeepingMtime`으로 방어). 동기화 충돌 사본은 '지금'을 받는다(`sync.mjs:552`) |

즉 지금은 **추정 위에 정렬을 얹고 있다.** 오늘 고친 세 지점(mtime 오염·충돌 사본·UTC 절단)은
전부 같은 뿌리의 다른 증상이다.

### 1-2. 중복 — "기억 유실 금지"와 "중복 금지"가 충돌한다

`saveNote(create:true)`는 슬러그 충돌 시 기존 노트를 덮지 않고 `-2`·`-3` 접미로 **분리 저장**한다
(`src/memory.mjs`, 주석: "서로 다른 주제가 같은 정규화 슬러그로 수렴해 앞 노트를 조용히 파괴하던
기억 유실 방지"). 과거 실제 유실 사고에서 나온 올바른 판단이다.

그 대가로 **같은 주제의 노트가 여러 벌 공존**한다. 파일 트리만으로는 "덮어쓰면 잃고, 안 덮으면
쌓인다" 사이에 출구가 없다. 버전 이력이 있어야 둘 다 만족한다.

### 1-3. 규모 — 매 턴 회사 기억 전체를 읽는다

```
saveHandover()  →  updateIndex()  →  vaultDocs()  →  journal·conversations·notes의 모든 .md 전문 읽기
autoLink()      →  vaultDocs() + 전 문서 TF-IDF·idf 재계산 (노트 저장 때마다 처음부터)
```

`saveHandover`는 **턴이 끝날 때마다** 불린다. 분리 검수 실측: 노트 500 + 일지 200에서
`updateIndex` 회당 79ms. 선형이므로 10만 문서면 턴마다 수 초~십수 초, `autoLink`의 TF-IDF
재계산까지 겹치면 그 이상이다. **이 벽은 미래가 아니라 지금 작동 중이고, 기억이 쌓일수록 제품이
느려진다** — 폴더 기억이 강점인 제품에서 치명적인 역인센티브다.

## 2. 목표 / 비목표

**목표**
- 같은 주제의 최신본이 항상 먼저 읽힌다 (추정이 아니라 기록으로).
- 노트를 갱신해도 옛 판이 남는다 — 덮어쓰기와 보존을 동시에.
- "왜 이렇게 바뀌었나"를 되짚을 수 있다 (개정 사유 + 그 개정을 만든 대화).
- 문서 10만 규모에서 턴 지연이 문서 수에 비례하지 않는다.

**비목표**
- 사용자에게 git을 노출하지 않는다. 일반 사용자 제품이다 — 커밋·브랜치·머지 용어가 UI에 나오면 실패.
- 자체 버전 관리 알고리즘을 만들지 않는다 (재구현 금지 원칙).
- 기억을 DB에 가두지 않는다. **폴더가 곧 기억**이라는 정체성은 불변이다.

## 3. 레퍼런스 관찰 (gujo-wiki, 유건 제공 화면)

`판 4` · `역사(4)` · 각 판의 **개정 사유** · **"이 개정의 사고과정(대화기록)"** 링크 · 근거/반박/무결성.

Argo 대응: 커밋 = 판, 커밋 메시지 = 개정 사유, 그 턴의 일지 = 사고과정. 지금 구조로는
덮어쓰는 순간 이유가 사라져 **원리적으로 불가능**하다.

> 출처 표기: 이 절은 유건이 제공한 참조 제품의 화면 관찰이다. Argo의 확정 스펙이 아니라 도착점의
> 예시로만 쓴다 — 참조 제품의 UI 규칙을 Argo에 그대로 이식하지 않는다.

## 4. 계층 구조 (결정)

```
정본   vault/ 의 md 파일          ← 사람이 읽고 고치는 것. 지금과 동일. 불변.
이력   .argo/git (blob·커밋)      ← 주제 노트의 판. 사용자에게 안 보임.
캐시   .argo/index.sqlite         ← 검색·정렬·링크. 지워도 정본에서 100% 재구축.
```

**세 층의 서열이 규칙이다.** 캐시와 이력은 언제든 버리고 정본에서 다시 만들 수 있어야 한다.
이 서열이 깨지면 "폴더가 곧 기억"이 거짓이 된다.

## 5. P1 — sqlite 캐시 (먼저 한다)

### 5-1. 왜 이걸 먼저 하나 (순서 근거 — 초기 판단을 뒤집었다)

처음엔 "캐시는 정본의 그림자이니 git 먼저"로 봤다. 재검토 결과 **틀렸다**:

- git으로 가도 **작업 트리는 그대로 md 파일**이다(§6-1 Option C). 인덱서가 읽는 대상이 안 바뀌므로
  재작업은 `blob_oid` 컬럼 추가와 이력 질의 정도다 — 내가 재작업 위험을 과대평가했다.
- 성능 벽은 **매 턴 이미** 작동 중이다. 정확성은 `836d26d`로 지혈됐지만 규모는 지혈이 없다.
- sqlite는 **되돌리기 쉽다**(지우면 재구축). git 정본화는 동기화·암호화·패키징을 동시에 건드리는
  큰 수술이고, §6-3의 위협 모델 결정이 남아 있다.

### 5-2. 의존성 0 — 검증됨

`node:sqlite`(Node 22 내장)가 **FTS5까지 동작**함을 이 설계 작업에서 실행 확인했다:

```
node -e "const s=require('node:sqlite'); ... CREATE VIRTUAL TABLE t USING fts5(body) ... MATCH '절차'"
→ node:sqlite 사용가능, FTS5: [{"body":"배포 절차 태그 푸시"}]   (node v22.22.3)
```

새 npm 의존성도, 네이티브 빌드도, Tauri 패키징 부담도 없다. **단 `ExperimentalWarning`이 뜬다** —
Node 메이저 업그레이드 시 API 변경 가능성을 감수해야 한다. 이게 유일한 비용이며, 대안(better-sqlite3)은
네이티브 모듈이라 3플랫폼 데스크톱 빌드에 부담을 준다.

### 5-3. 스키마 (초안)

```sql
CREATE TABLE docs (
  rel        TEXT PRIMARY KEY,   -- 'notes/배포-절차.md' (논리 경로, '/' 고정)
  kind       TEXT NOT NULL,      -- note | journal | weekly | legacy | conflict
  title      TEXT,
  updated    TEXT,               -- YYYY-MM-DD (로컬)
  updated_exact INTEGER NOT NULL,-- 1=frontmatter/커밋 근거, 0=mtime 추정
  mtime_ms   INTEGER NOT NULL,
  hash       TEXT NOT NULL,      -- 내용 해시 — 증분 갱신 판정 키
  blob_oid   TEXT,               -- P2에서 채움
  size       INTEGER NOT NULL
);
CREATE INDEX docs_order ON docs(kind, updated DESC, mtime_ms DESC);
CREATE VIRTUAL TABLE docs_fts USING fts5(rel UNINDEXED, title, body, tokenize='trigram');
CREATE TABLE links (src TEXT, dst TEXT, score REAL, PRIMARY KEY (src, dst));
CREATE TABLE meta (k TEXT PRIMARY KEY, v TEXT);  -- schema_version, last_scan
```

**토크나이저는 `trigram`**을 기본으로 둔다 — 기본 `unicode61`은 한국어를 공백 단위로만 끊어
조사가 붙은 어절이 검색에 안 걸린다. 현재 `tokens()`가 한글을 2gram으로 쪼개는 것과 같은 이유다.
(trigram 대 한글 2gram의 재현율 비교는 **미검증** — P1 착수 시 실측한다.)

### 5-3-1. 실제 착수 범위 — P1a / P1b 분리 (2026-07-26 구현 중 조정)

P1을 한 번에 다 하지 않는다. 비용이 가장 큰 곳은 **매 턴** 불리는 `updateIndex`이고, `autoLink`는
노트 저장 때만 불린다. 최소 출하 단위로 가른다.

| 단계 | 내용 | 상태 |
|---|---|---|
| **P1a** | 메타 인덱스(`docs` 테이블) + `updateIndex` 캐시 경유 + 폴백·킬스위치 | 구현됨 |
| P1b | FTS5 + `autoLink` 후보 축소(전 문서 TF-IDF 재계산 제거) | 미착수 |

따라서 아래 §5-3의 `docs_fts`·`links` 테이블과 §5-4의 4번 항목은 **P1b 범위**다. P1a에서는
`autoLink`가 여전히 `vaultDocs()`로 전수 읽기를 한다 — 노트 저장 시에만 발생하는 비용이다.

**P1a 구현 메모(코드와 어긋나면 코드가 맞다)**

- 판정 정본은 `src/vaultdoc.mjs` 한 곳(`docMeta`·`docKind`·`noteDate`·`localDay`). 캐시 경로와
  정본 경로가 이 모듈을 **함께** 쓴다 — 두 벌로 두면 캐시가 정본과 다른 판정을 하게 된다.
- 변경 판정 키는 해시가 아니라 **mtime + size**다. 해시를 쓰려면 전수 읽기가 필요해 목적과 모순이다.
  ⚠ "내용이 바뀌었는데 둘 다 같은 경우는 실제 경로에선 발생하지 않는다"는 초판 서술은 **철회했다**
  (2라운드 검수가 재현: appendLink는 append가 아니라 링크 섹션 재조립이라 중복 제거·공백 정규화로
  줄어든 크기가 새 링크와 상쇄될 수 있다). 그래서 mtime을 심는 쓰기 경로 **2곳 모두** 명시적으로
  캐시를 무효화한다 — `writeKeepingMtime`(memory.mjs, 역링크)과 동기화 수신 `writeLocal`(sync.mjs,
  원격 mtime 이식 시 vault md 한정) → `invalidatePath`.
- `ARGO_MEMINDEX=0` 킬 스위치 — 캐시를 의심할 때 정본 경로로 즉시 되돌린다. 동등성 테스트도 이걸 쓴다.
- **문서화된 잔여(3라운드 검수 F2)**: 내용·mtime·size가 전부 그대로인 채 **읽기 권한만** 잃은 파일은
  캐시가 스캔에서 아예 읽지 않아 옛 행이 남고, 정본 폴백은 읽기를 시도해 뺀다 — 이 실패 모드에선 두
  경로가 갈린다. 감지하려면 매 스캔 파일마다 access() 왕복(스캔 비용 ~2배)이라 수용하지 않았다.
  즉 HIGH-4(읽기 실패 동등성)는 "변경 후 읽기 불가" 절반만 닫혔고 "무변경 채 읽기 불가"는 열려 있다.
- **스캔 불건전 보호(3라운드 F3)**: 행이 있던 폴더의 readdir 실패(권한·마운트) 또는 한 턴 20개 초과
  읽기 실패(fd 폭주)는 삭제·쓰기를 보류하고 그 턴만 정본 폴백한다 — 일시 장애가 캐시 전량 삭제 →
  회복 후 11~13초 재구축으로 번지지 않게. 폴백도 같은 장애를 겪으므로 산출물 동등성은 유지된다.
- DB 위치는 워크스페이스 루트의 `.index.sqlite`, 동기화 제외는 `sync.mjs` EXCLUDE의 **구조적 제외
  블록**에 넣었다(암호화 판정보다 앞 — 2026-07-23 검수 CRITICAL의 순서 불변식).

### 5-4. 증분 갱신

1. 스캔은 `readdir` + `stat`만 한다. `hash`는 mtime·size가 바뀐 파일만 다시 계산한다.
2. 바뀐 문서만 `docs`·`docs_fts` upsert, 사라진 문서는 delete.
3. `updateIndex()`는 전문 읽기를 그만두고 **`docs` 질의 결과를 렌더링**한다. `_index.md`는 정본이
   아니라 산출물이 된다(크루·사장이 읽을 수 있게 파일로는 계속 쓴다).
4. `autoLink()`의 TF-IDF 전체 재계산을 제거한다. df/idf를 `docs_fts`에서 얻고, 후보를 FTS로 좁힌
   뒤 그 후보에만 유사도를 계산한다.

### 5-5. 재구축 가능성 — 이게 안전장치다

- `meta.schema_version`이 코드와 다르면 **DB를 지우고 전체 재구축**한다. 마이그레이션을 쓰지 않는다
  — 캐시라서 그래도 되고, 그래야 캐시로 남는다.
- DB 파일은 **동기화 제외**다(`sync.mjs`의 제외 목록에 추가). 기기마다 자기 캐시를 갖는다.
  `.gateway*`·`*.status.json`·`.sync-state.json`과 같은 계열이다.
- 크래시·손상 시 열기 실패하면 지우고 재구축한다. 이 경로를 반드시 테스트한다.

### 5-6. P1 검증법 (관문)

| 항목 | 방법 | 통과 기준 |
|---|---|---|
| 정확성 동일성 | 같은 vault에 대해 신·구 `updateIndex` 산출물 비교 | `_index.md` 바이트 동일(정렬 규칙 유지) |
| 증분 정확성 | 파일 추가·수정·삭제·이름변경 후 재스캔 | 전체 재구축 결과와 동일 |
| 재구축 | DB 삭제 후 재기동 / DB 고의 손상 | 자동 재구축, 데이터 손실 0 |
| 규모 | 합성 vault 10만 문서 벤치 | **§5-7 참조 — 최초 목표 200ms는 근거 없이 잡은 값이었고 실측으로 폐기했다** |
| 격리 E2E | 임시 `ARGO_ROOT` + 빈 포트, 실제 턴 흐름 | 큐·핸들러 계열 교훈 적용 — 단위 테스트만으로 닫지 않는다 |
| 동기화 미오염 | DB가 매니페스트에 안 오르는지 | 제외 목록 회귀 테스트 |

## 5-7. 규모 실측 (2026-07-26, 문서 10만 = 노트 5만 + 일지 5만)

macOS, Node v22.22.3, 임시 `ARGO_ROOT`. "턴" = 일지 1개 append 후 `updateIndex` 1회(실제 턴의 모양).

| 경로 | 턴당 |
|---|---|
| 변경 전(정본 전수 읽기) | **8,427 / 9,686ms** (2회 측정 평균) |
| 캐시, `stat` 직렬 | p95 **1,927ms** |
| 캐시, `stat` 병렬(512) | p95 **1,000ms** · 중앙값 972ms — **트랜잭션 도입 전 측정.** 이후 측정(결론 3)은 1,226ms인데 느려진 게 아니라 머신 편차다: 같은 실행의 대조군(전수 읽기)도 9.7→12.3초로 함께 흔들렸고 배율(~10배)은 유지된다 |

최초 구축(캐시가 빈 상태에서 전 문서 1회 읽기)은 11.5~13.2초. 1회성이다.

**내역 분해** (같은 규모, 별도 프로파일):

| 구간 | 시간 |
|---|---|
| `readdir` 2개 디렉터리 | 70ms |
| `stat` 10만 (직렬) | 1,275ms |
| `stat` 10만 (병렬 512) | **363ms** ← 스캔의 바닥 |
| 전체 행 `SELECT` + `JSON.parse` | 266ms |
| 렌더 대상만 질의(상한 있음) | 8ms |

### 결론 1 — 200ms 게이트는 폐기한다 (근거 없이 잡은 값)

스캔을 하는 한 `stat` 전수 스윕 **363ms가 물리적 바닥**이다. 200ms는 이 문서를 쓸 때 실측 없이
적은 숫자였고, 측정으로 반증됐다. 숫자를 맞추려 게이트를 조용히 낮추지 않고 폐기한다.

- **현재 달성**: 10만 문서에서 턴당 **1.0~1.2초**(변경 전 대비 ~10배 — 절대값은 측정마다 머신 편차, 배율은 유지). 실사용 규모(현재 최대 노트 25개)에선
  전 구간 무시 가능하다 — 이 표는 스트레스 테스트지 오늘의 현실이 아니다.
- ~~**상한을 도입하면** 400ms대 예상~~ → **틀렸다. 실측하니 개선 없음**(아래).
- **그 아래로 가려면** 스캔 자체를 없애야 한다(파일 감시/FSEvents). 별건이며 자체 실패 모드가 있다.

### 결론 3 — 상한은 산출물 문제를 고쳤지만 턴 지연은 못 줄였다 (예상 정정)

상한 도입 전후 실측(같은 머신·같은 시드, 트랜잭션 반영 후):

| | 최초 구축 | 턴 p95 |
|---|---|---|
| 상한 없음 | 4,707ms | 1,273ms |
| **상한 200** | 4,574ms | **1,226ms** |

"렌더가 8ms로 떨어지니 400ms대"라는 내 예상은 **빗나갔다.** 렌더는 지배 항목이 아니었다. 남은 비용은
`stat` 스윕 363ms + 전체 행 `SELECT`·`JSON.parse` 266ms + 10만 건 정렬, 즉 **"전부 적재한다"는 구조**
자체다. 상한은 렌더만 줄일 뿐 적재를 줄이지 않는다.

그래도 상한은 유지한다 — 고친 문제가 다르기 때문이다. **상한이 고친 것은 속도가 아니라 산출물이다**:
5만 줄짜리 인덱스가 크루의 첫 화면이 되고 컨텍스트를 통째로 먹던 것을 200줄로 되돌렸다. 이게 §5-7
결론 2에서 지적한 진짜 문제였고, 그건 해결됐다.

턴 지연을 더 줄이려면 **적재 자체를 줄여야** 한다 = 렌더 스펙(구간·정렬·상한)을 SQL로 내리는 것.
지금 하지 않은 이유는 캐시·폴백 두 경로가 갈릴 위험이며, 그 동등성이 이 캐시의 유일한 계약이다.
필요해지면 **공용 스펙 하나를 두 경로가 함께 해석**하는 형태로만 내린다.

### 결론 2 — 진짜 문제는 속도가 아니라 산출물 크기다 (제품 결정 필요)

`_index.md`는 **주제 노트를 전량 나열**한다. 노트 5만이면 5만 줄짜리 인덱스가 만들어지고, 그게
크루가 기억을 여는 첫 화면으로 들어간다. 캐시는 그걸 **더 빨리 만들 뿐**, 쓸모없다는 사실은 그대로다.
위 표의 `SELECT` 266ms도 여기서 나온다.

**결정됨(2026-07-26 유건 승인) — 상한을 도입한다.** 주제 노트 200개, 충돌 사본 20개.

- 잘린 나머지는 **사라지는 게 아니라** 파일로 그대로 있다. 인덱스에 "최근 200개만 실었다 / 나머지 N개도
  그대로 남아 있으니 `vault/notes/`를 Grep으로 찾아라 / 없다고 단정하지 마라"를 명시한다. 크루가 인덱스
  부재를 "지식 없음"으로 오독하는 것이 이 상한의 유일한 위험이라, 그 문장이 상한의 일부다.
- 상한은 **렌더 단계에서** 적용한다(캐시·폴백 공통). SQL LIMIT으로 내리면 두 경로가 갈릴 위험이 생기고,
  그 동등성이 이 캐시의 유일한 계약이다. 질의 최적화는 필요해지면 그때 공용 스펙으로 내린다.

## 6. P2 — git blob 정본화 (나중에 한다)

### 6-1. 동기화와의 접점 — Option C 권장

현재 동기화는 회사별 `__manifest__.json`(경로→`{m,s,h}`) 기준 **파일 단위**이고, 변경 판정이
**해시 우선**이다(`sync.mjs:438`, `h`는 `:243`에서 항상 채워짐). 텍스트 충돌은 원격을 정본으로
받고 로컬본을 `.conflict-*.md`로 양쪽 보존한다(`sync.mjs:550-556`).

| 안 | 내용 | 판정 |
|---|---|---|
| A | 파일만 동기화, git은 기기 로컬 이력 | **기각** — 기기마다 이력이 갈려 "판 4"가 기기마다 다르다. 이력이 정본이 될 수 없다 |
| B | git 자체를 동기화 단위로(fetch/push) | 기각(지금은) — `sync.mjs` 전면 교체. 큰 수술 |
| C | **`.git/objects/**`를 기존 파일 동기화에 태운다** | **권장** |

Option C의 핵심: git object는 **내용 주소**라 파일명이 곧 내용 해시다. 같은 이름이면 반드시 같은
내용이므로 **파일 단위 LWW가 원리적으로 무해**하다 — 지금의 동기화 엔진을 거의 그대로 쓰면서
이력이 기기 간에 공유된다. 조심할 건 가변인 `refs`뿐이고, 기기별 ref(`refs/devices/<deviceId>`)로
쓰면 충돌 자체가 없어진다. 병합은 각 기기가 로컬에서 수행한다.

부수 효과: `.conflict-*.md`가 3-way 병합으로 대체된다(`836d26d`에서 별도 섹션으로 격리한 그 파일들).

### 6-2. 무엇을 버전 관리하나 (결정)

**주제 노트(`vault/notes/`)만.** 일지는 append-only 원본이라 매 턴 커밋하면 object가 폭증한다.
레퍼런스 화면에서도 판이 붙는 건 위키 문서이지 로그가 아니다. `projects/`·`files/`는 후속 판단.

이 결정으로 `saveNote(create:true)`의 `-2`·`-3` 분리 저장이 **불필요해진다** — 덮어쓰되 옛 판은
커밋에 남는다. §1-2의 딜레마가 여기서 풀린다. (기존 `-2`·`-3` 파일의 병합은 마이그레이션 과제.)

### 6-3. 암호화와의 접점 — 미결, 결정 필요

`ARGO_ENC_VAULT=1`이면 `isEncRel`이 모든 rel에 true가 되어 봉투 암호화가 걸린다(`sync.mjs:47` 주석).
git object에 봉투를 씌우면:

- object는 이미 zlib 압축된 불투명 바이너리다 → 이중 압축, 델타 압축 이득 상실.
- object **파일명이 평문 해시**로 남는다. 해시에서 내용을 복원할 순 없지만, 내용을 아는 공격자가
  존재 여부를 확인할 수 있다(사전 공격). 파일명까지 가명화할지는 **위협 모델을 정해야** 답이 나온다.

**이건 P2 착수 전 유건 결정 사항으로 남긴다.** 스토리지 운영자를 신뢰 경계 밖으로 볼 것인가.

### 6-4. 구현 의존성 — 미검증

시스템 `git` 바이너리는 일반 사용자 맥에 없을 수 있다(Xcode CLT 필요). 순수 JS 구현
(isomorphic-git 계열)이 데스크톱 패키징에 맞을 것으로 **추정**하나, 번들 크기·성능·Windows 경로
처리는 실측하지 않았다. P2 착수 시 스파이크로 확인한다.

### 6-5. 개정 사유 — 크루가 이유를 남기게

`saveNote(wsId, title, content, { reason })`를 추가해 커밋 메시지로 쓴다. 정리 데몬은 자동 생성,
크루는 프롬프트로 유도한다. 이유 없는 갱신은 막지 않는다(막으면 기록 자체를 안 하게 된다).

> 관련: 분리 검수가 남긴 LOW-2 — 크루 프롬프트에 "노트에 `updated:` frontmatter를 남겨라"를
> 넣는 건은 이 항목에 흡수된다. 다만 프롬프트 지시는 러너(SDK/Codex/Gemini/GLM/Kimi)별 준수율이
> 다르므로 **라이브 턴 검증 후** 반영한다 — "프롬프트는 힌트, 코드가 보장" 원칙.

### 6-6. P2 검증법

| 항목 | 방법 | 통과 기준 |
|---|---|---|
| 이력 정확성 | 노트 N회 갱신 후 판 목록·개정 사유 대조 | 판 수·순서·사유 일치 |
