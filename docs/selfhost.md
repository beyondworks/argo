# Argo 서버 설치 (리눅스 VPS — 1차)

> 배포 경로: 데스크톱 앱(dmg·서명·공증, argo-agent Latest)이 정문이고, 서버 설치는 리눅스 VPS·헤드리스용 병행 경로다.
> 두 가지 방식이 있다 — **계정 모드(기본)**: 앱과 같은 계정·같은 회사로 에이전트를 24시간 켜 둔다.
> **로컬 모드(`--local`)**: 로그인 없이 그 서버 안에서만 쓰는 웹 화면 서버.

## 계정 모드 설치 (기본 — 리눅스 x64, Node 22+)

앱을 꺼도 메신저·텔레그램·예약 작업에 에이전트가 답하게 하는 방식이다.

```bash
curl -fsSL https://github.com/beyondworks/argo-agent/releases/latest/download/install.sh | bash
argo                    # 처음 한 번 로그인(서버에 브라우저가 없으면 안내에 나오는 ssh -L 명령을 내 PC에서 먼저 실행)
argo service install    # 재부팅·크래시에도 다시 켜지는 상주 — 이 서버가 실행 담당을 맡는다
```

- `argo`만 치면 대화 화면이다(에이전트와 대화, `/help`로 명령 보기, `/quit`·`exit`로 나가기).
- AI 연결 정보(API 키 등)는 기기마다 따로다 — 서버에서 `/ai`로 한 번 연결한다(클라우드로 보내지 않는다).
- 여러 기기에서 같은 회사를 쓰는 동기화는 Pro 플랜이다.
- 업데이트 = 같은 명령 재실행(상주 중이면 새 버전으로 다시 시작한다).
- 다른 프로그램의 `argo` 명령(예: Argo Workflows CLI)이 이미 있으면 덮어쓰거나 가리지 않고 등록을 건너뛴다 — 설치 끝에 나오는 전체 명령(`node …/bin/argo.mjs`)으로 실행한다.

## 로컬 모드 설치 (`--local` — 로그인 없음)

```bash
curl -fsSL https://github.com/beyondworks/argo-agent/releases/latest/download/install.sh | bash -s -- --local
```

하는 일: 최신 서버 타르볼 설치(`~/.argo-selfhost/app`) → systemd user 서비스(`Restart=always` + linger) →
`127.0.0.1:3001` 기동 → `/api/ping` 신원 검증. **업데이트 = 같은 명령 재실행**(데이터는 `~/.argo-selfhost/data` 보존).
이미 로컬 모드로 쓰던 서버는 `--local` 없이 다시 실행해도 로컬 모드로 업데이트된다. 로컬 모드에는 `argo` 명령을 등록하지 않는다
(같은 데이터 폴더에서 계정 로그인이 섞이면 로그인이 풀릴 수 있다).

## 보안 기본값 (install.sh가 강제 — 바꾸기 전에 읽을 것)

- **루프백 바인딩 + 로컬 모드(무인증)** — 원격 사용은 SSH 터널:
  `ssh -L 3001:127.0.0.1:3001 user@서버` 후 브라우저에서 `http://localhost:3001`
- **포트를 공개로 열지 말 것.** 무인증 공개 = 회사(에이전트·기억·자격) 전체가 인터넷에 노출된다.
  공개 접근이 필요하면 인증 모드(Supabase env로 빌드) — 후속 문서.
- 기본 서버 타르볼은 **로컬 1인 모드**다. 기기 간 동기화·팀 메신저 에이전트 브리지는 같은 Supabase에 로그인한 인증 모드에서 동작한다. 아래 회사 서버 절의 재빌드 절차가 필요하다.
- 지원 배포물: 데스크톱 Argo·Argo Messenger는 macOS Apple Silicon/Intel 및 Windows x64, 셀프호스트 타르볼은 Linux x64다. Linux용 Messenger 데스크톱이나 ARM Linux 타르볼을 제공한다는 뜻은 아니다.

## 러너 연결 (헤드리스)

- **API 키**: 설정 → 러너 연결에 붙여넣기(저장 시 실검증 — 무효면 저장 안 됨).
- **Codex/Gemini OAuth**: "로그인 페이지 열기" → 노트북 브라우저에서 승인 → 리다이렉트된 주소를 복사해 붙여넣기(콜백은 서버에 못 오므로 붙여넣기 폴백이 정식 경로).
- **Claude**: 노트북 터미널에서 `claude setup-token` → 출력 토큰 붙여넣기(줄바꿈 섞여도 자기치유).

### base URL을 손대지 말 것 (2026-09-05 실사용 장애)

러너 base URL은 Argo가 러너마다 정한다. env로 덮을 수 있지만 **끝에 `/v1`을 붙이면 안 된다** — Argo가
`/v1/messages`를 덧붙이므로 경로가 겹쳐 전 모델이 404가 되고, 화면에는 "선택한 모델에 문제가 있습니다"로
보인다(모델을 바꿔도 같다). 정본 값:

| env | 정본 값 |
|---|---|
| `OPENROUTER_BASE_URL` | `https://openrouter.ai/api` |
| `GLM_BASE_URL` | `https://api.z.ai/api/anthropic` |
| `KIMI_BASE_URL` | `https://api.moonshot.ai/anthropic` |
| `GROK_BASE_URL` | `https://api.x.ai` |

같은 404는 OpenRouter 계정의 데이터 정책이 모든 제공사를 제외했을 때도 난다
(<https://openrouter.ai/settings/privacy>). 서버의 아웃바운드 프록시가 대신 응답하는 경우도 같은 증상이다.

## 회의실 동시 발언 상한

회의실에서 여러 에이전트를 부르면 동시에 발언한다(릴레이 `@A > @B` 제외). 동시 실행 상한은 `ARGO_ROOM_CONCURRENCY`(기본 8, 1~16으로 클램프). Claude 러너는 에이전트마다 CLI 프로세스를 띄우므로 메모리가 작은 서버는 3~4를 권한다. 에이전트 쪽지함 배달도 같은 방식으로 동시에 돈다 — 상한은 `ARGO_MAIL_CONCURRENCY`(기본 8, 1~16). **이 상한은 회사당**이라 회사가 여럿이면 실동시 턴은 회사 수만큼 곱해진다(매 분 자동 배달이므로 메모리가 작은 서버는 회의실과 같이 3~4를 권한다). 같은 에이전트 앞으로 온 쪽지는 그 에이전트 안에서 순차다(상한은 사실상 "동시에 도는 에이전트 수"). 착수는 에이전트별 라운드로빈이라 한 에이전트에 밀린 백로그가 다른 에이전트의 쪽지를 막지 않는다.

## 24/7 활용

루틴·텔레그램/슬랙 게이트웨이가 노트북 수면과 무관하게 상시 동작 — VPS가 리더 기기가 된다.

## 맥 우선·서버 예비 (`--standby`)

맥과 서버(VPS)에 같은 계정으로 로그인해 두고, **맥이 켜져 있는 동안은 맥이**, 맥이 꺼지거나 연결이 끊기면 **서버가** 메신저·예약 작업을 맡게 하는 구성이다.
맥이 다시 켜지면 맥이 되찾는다. 기억·대화는 동기화로 이어진다.

실행 담당 역할은 세 가지다. 더 높은 역할의 기기는 낮은 역할이 맡고 있어도 가져오고(러너가 연결돼 있을 때만), 같은 역할끼리는 먼저 맡은 기기가 계속 맡는다.

| 역할 | 띄우는 방법 | 맡는 때 |
|---|---|---|
| 우선 | `argo service install` (기본) | 늘 이 서버가 맡는다 |
| 일반 | 맥 앱·맥 상주, `argo run --no-prefer` | 우선 기기가 없으면 |
| 예비 | `argo service install --standby` | 다른 기기가 맡고 있지 않을 때만 |

### 서버에서 한 번 (계정 `crew` 예시)

1. 설치·로그인: 위 "계정 모드 설치"대로 `install.sh` → `argo`로 **맥과 같은 계정**에 로그인한다.
2. AI 연결 — 연결 정보는 기기마다 따로라 맥의 연결이 서버로 넘어가지 않는다. 같은 AI 계정을 서버에서 한 번 더 연결한다. 계정 인증은 사용자가 직접 한다.
   - Claude: **맥 터미널**에서 `claude setup-token` → 출력된 토큰을 서버의 `argo` 대화 화면 `/ai` → Claude → OAuth에 붙여넣는다(저장할 때 실제로 검증한다).
   - Codex: 서버에서 `codex login --device-auth` → 나온 주소를 내 PC 브라우저에서 열고 코드를 입력한다(서버에 브라우저가 없어도 된다). `codex` 명령이 없으면 `npm i -g @openai/codex`로 설치한다.
     그다음 `argo` → `/ai` → Codex → "이 컴퓨터 로그인 사용". 기기 코드 로그인을 쓸 수 없는 버전이면 내 PC에서 `ssh -L <로그인 안내에 나오는 포트>:localhost:<같은 포트> crew@서버`로 터널을 연 채 서버에서 `codex login`을 실행한다.
   - 연결이 하나도 없으면 서버는 맥의 리스가 만료된 뒤에도 160초를 더 기다린다(맥이 꺼지고 약 4분 40초 뒤에 맡는다). 맡아도 "AI 연결 필요" 안내로만 답한다.
3. linger — 로그아웃·재부팅 뒤에도 상주가 돌게 한다. 내 계정이라도 SSH 셸에서는 보통 관리자 권한이 필요하다:
   `sudo loginctl enable-linger crew` (`argo service install`이 켜 보고, 꺼져 있으면 이 명령을 안내한다).
4. `argo service install --standby` — 서비스 파일의 실행 명령이 `argo run --standby`가 된다(업데이트해도 그대로 유지된다).
   이미 `argo service install`로 등록해 둔 서버는 `--standby`를 붙여 다시 실행하면 바뀐다.

맥의 Argo 앱도 이 버전 이상이어야 되찾는다. 옛 버전 맥은 서버가 맡고 있으면 양보만 한다(서버가 담당을 계속 쥔다).

### 넘어가는 시간과 확인

실행 담당 판정(리스 읽기·갱신)은 파일 동기화와 따로 8초마다 돈다 — 큰 파일을 올리거나 첫 동기화가 오래 걸려도 판정은 밀리지 않는다.

- 맥이 꺼지거나 잠들면: 맥의 리스가 만료되는 120초 뒤 다음 판정(최대 8초)에 서버가 맡는다 — 약 2분. 서버가 맥을 두 대 이상 본 적 있으면 두 판정(16초)을 더 기다린다
  (남은 맥이 먼저 맡게) — 약 2분 20초.
  메신저는 그 뒤 게이트웨이 확인(10초 주기)에서 받기 시작하고, 그 사이 온 글은 서버 커서부터 이어서 처리한다.
  맥이 잠들기 직전에 이미 맡아 실행을 시작한 글은 맥이 깨어나야 끝난다(실행권을 다른 기기로 넘기지 않는다).
- 맥이 다시 켜지면: 맥은 먼저 30초 동안 깨어 있는지 본다. 뚜껑을 닫아 둔 맥도 몇 초씩 깨어나는데(Power Nap 등), 그때마다 리스를 가져갔다가 다시 잠들면 서버는 물러나고 맥은 맡지 못해
  2분 가까이 아무도 맡지 않았다. 30초가 지나면 맥이 리스를 다시 쓰고 22초(판정 두 번 + 6초)를 기다린 뒤 맡는다 — 보통 깨고 55~65초. 그동안은 서버가 계속 맡다가,
  맥의 글을 읽으면(8초 안) 물러난다. 서버가 그 글을 못 읽어도(서버의 리스 읽기가 걸리거나 계속 실패) 서버는 마지막으로 자기 글을 확인한 뒤 18초가 지나면 스스로 물러나므로,
  맥이 맡기 시작할 때 서버는 이미 물러나 있다. 맥은 기다리는 시간을 자기 리스 쓰기의 응답을 받은 뒤부터 센다 — 쓰기가 서버에 늦게 닿아도(업로드 지연) 겹치지 않는다.
  두 기기가 함께 맡는 시간은 실측(100ms 단위, PR #884의 장면들)에서 0이었다. 남는 조건은 그 사이 어느 쪽 벽시계가 크게 뛰지 않는 것이다(시계 점프 — 4초 여유를 넘으면
  그만큼 겹칠 수 있다). 대신 서버가 물러난 뒤 맥이 시작할 때까지 약 20초는 아무도 맡지 않는다(그 사이 예약 작업은 다음 확인 때 돈다).
  맥에서 바로 대화를 보내 동기화가 연달아 돌아도 이 기다림은 줄지 않는다.
  잠들었던 맥은 리스를 다시 확인하기 전까지 자기가 맡는다고 보지 않는다 — 서버가 이미 돌린 루틴을 깨어난 맥이 다시 돌리지 않는다.
- 최근 14일 안에 다른 기기를 본 기기(같은 계정 — 데이터 폴더의 `.lease-peer.json`, 계정마다 따로): 자기 리스를 마지막으로 확인한 뒤 18초까지만 맡는다. 그래서 로그인이 끊기거나
  네트워크가 끊긴 동안에는 맡지 않는다 — 맥 앱을 세션이 끊긴 채 켜도 서버와 함께 맡지 않는다. 서버를 없앴다면 14일 뒤(또는 다른 계정으로 로그인하면 바로) 혼자 쓰는 기기로 돌아간다.
- 다른 기기를 본 적 없는 맥(혼자 쓰는 기기): 종전처럼 맡는다. 다만 리스를 읽지 못하면(서버 오류·네트워크) 이미 맡고 있던 경우가 아니면 맡지 않는다 — 처음 만나는 서버와
  겹치지 않게. 켜자마자 읽기가 한 번 실패하면 1초 뒤 한 번 더 읽는다(읽기가 응답 없이 걸리면 5초 뒤 맡았다가, 30초 시간 초과로 실패가 확인되면 내려놓고 다시 읽는다). 오프라인으로 켜면 네트워크가 돌아올 때까지 맡지 않는다(그동안은 AI 호출·메신저·연결 서비스가 어차피 안 된다).
  로그인이 끊긴 채 켜면(동기화 자체가 안 됨) 종전처럼 맡는다.
- 리스를 읽지 못한 판정(네트워크 오류·서버 오류·로그인 만료)은 "리스 없음"으로 보지 않는다 — 그 판정에서는 리스를 쓰지 않는다. 로그에는 `리스 읽기 실패`로 남는다.
  120초 넘게 한 번도 읽지 못하면 2분에 한 번만 다시 써 본다(깨진 리스 파일이 모든 기기를 영영 막지 않게). 써 본 뒤 확인 읽기도 실패하면 읽기가 돌아올 때까지 다시 쓰지 않는다.
- 서버의 동기화가 끊기면(로그인 만료 등) 서버는 맡지 않는다 — 맥이 맡고 있는지 알 수 없어서다. 맥도 꺼져 있으면 그동안 아무도 맡지 않는다.
  `journalctl --user -u argo-cli`에 `기기 세션 갱신 실패 — 재로그인 필요`가 보이면 서버에서 `argo`로 다시 로그인한다.
  예비 서버에서 동기화를 꺼 두면(`ARGO_SYNC=0`, 로그아웃) 같은 이유로 아무것도 맡지 않는다.
- 지금 누가 맡는지: 맥 앱 설정 → 동기화에 "이 기기가 실행 담당"이 보이는지, 서버는 `journalctl --user -u argo-cli -f`의 `실행 리더 획득`·`실행 리더 양보` 줄.

### 서버가 맡는 동안 안 되는 것

- 맥에만 있는 폴더·파일: 맥에서 고정한 작업 폴더, 바탕화면·문서·프로젝트 폴더는 서버에 없다. 서버에서 도는 에이전트는 이 사실을 안내받아, 그런 파일이 필요한 일이면 지금은 열 수 없다고 답하고 맥이 켜지면 이어서 하자고 말한다.
  회사 폴더 안의 파일은 동기화돼 서버에서도 쓸 수 있다. 서버에서 회사 폴더 밖에 저장한 파일은 서버에만 남는다.
- 맥에서 연결한 텔레그램 봇: 봇 토큰은 연결한 기기에만 있어(클라우드로 보내지 않는다) 맥이 꺼지면 받지 않는다. 서버에서도 같은 봇을 연결하면 먼저 받기 시작한 기기가 계속 받는다 — 텔레그램 봇에는 맥 우선 규칙이 적용되지 않는다.
- 맥 경로를 적어 둔 루틴: 서버가 맡은 날에는 그 경로를 찾지 못한다(루틴 저장 화면의 기기 경로 안내와 같다).

### 맥이 켜져 있으면 서버가 이어받지 않는 경우

- 맥의 AI 연결이 끊겨도(Claude 로그인 만료 등) 맥이 켜져 있고 동기화가 되는 동안은 맥이 계속 맡는다. 서버는 이어받지 않는다.
  그동안 메신저로 부른 에이전트는 다른 Argo가 받기를 기다렸다가(최대 160초) AI를 다시 연결하라는 안내로 답하고, 루틴도 맥에서 실패한다. 맥에서 AI를 다시 연결하면 된다.

## 빌드·검증 이력

- 타르볼 = `scripts/stage-server.mjs`(stage-sidecar와 동일 조립 계약: standalone+static/public+SDK 네이티브+시크릿 유출 가드). CI `server` 잡(ubuntu, 릴리스 자산에 `argo-server-<ver>-linux-x64.tar.gz` + `install.sh` 동봉).
- 릴리스 CI는 배포 타르볼을 새 디렉터리에 추출하고 빈 HOME·임시 데이터에서 서버를 기동한다. `/api/ping` 버전/빌드, 홈 200, 로컬 사용자 인증 모드, 외부 Host 421, 로컬 자산 탐색 경로를 검사한다. 이는 실제 사용자 OAuth·벤더 호출 검증을 대체하지 않는다.
- 2차 예정: 맥/윈도 CLI 설치, Docker 이미지, `argo update` 전용 명령.

## 팀 메신저 (Argo Messenger) — 회사 서버로 운영하기

메신저의 서버는 **Supabase 프로젝트 하나**다(조직·채널은 그 안의 행, RLS가 조직 사이를 가른다). Argo 클라우드를
쓰지 않고 회사가 직접 운영하려면, 회사 소유의 Supabase(호스티드 프로젝트 또는 셀프호스트 스택)에 같은
마이그레이션을 적용하고 앱에서 서버만 바꾼다. 라이선스는 계약 기반이다(문의: 랜딩 "문의").

1. **전체 마이그레이션 적용** — 새 회사 Supabase에는 `supabase/migrations/`의 선행 인증·회사·플랜 마이그레이션부터 해당 릴리스까지 빠짐없이 적용한다. 이미 운영 중이면 `supabase migration list`로 적용 이력을 확인한 뒤 누락된 항목만 순서대로 적용한다. 운영 프로젝트를 reset하지 않는다. 동기화 색인 RPC(`20260910120000_sync_index_rpc.sql`)를 아직 적용하지 않았으면 앱은 종전 `storage.list` 경로로 폴백해 동작한다 — 새 기기의 회사 발견이 느리거나(RLS 아래 전수 스캔) 타임아웃될 수 있으니 적용을 권한다. 메신저 기본 SQL 두 개만으로는 현재 앱을 운영할 수 없다. 이번 버전에 필요한 메신저 순서는 다음과 같다(선행 공통 마이그레이션을 대체하는 목록이 아니다):

   ```text
   20260903120000_msgr.sql
   20260907120000_msgr_crew_inventory.sql
   20260908120000_msgr_bots.sql
   20260908140000_msgr_crew_autodispatch.sql
   20260909000000_msgr_bot_external_id.sql
   20260909001000_msgr_crew_folder.sql
   20260909002000_msgr_profiles_friends.sql
   20260909003000_msgr_message_meta.sql
   20260909004000_msgr_p0_reads_reactions_prefs.sql
   20260909005000_msgr_avatars.sql
   20260909120000_msgr_execution_claims.sql
   20260909230000_msgr_bot_execution.sql
   20260914200000_msgr_delete_me.sql
   ```

   `20260909120000_msgr_execution_claims`·`20260909230000_msgr_bot_execution` 두 항목은 여러 기기가 같은 에이전트·봇을 실행할 때 중복 실행과 중복 응답을 막는 DB 계약이다. 모든 Argo 에이전트 호스트와 외부 봇 실행기도 같은 릴리스의 계약으로 갱신한 뒤 검수한다. 과거 SQL만 적용한 서버로 새 클라이언트를 연결하지 않는다.
   Messenger 0.1.18의 사람·에이전트 즐겨찾기와 1:1 나가기는 `20260912135036_msgr_target_favorites_dm_leave.sql`이 필요합니다. 앱을 업데이트하기 전에 적용하세요. 기존 대화·즐겨찾기 행을 삭제하거나 변환하지 않는 추가 마이그레이션입니다.

2. **첨부 버킷** — 기본 메신저 SQL은 첨부 버킷을 만들지 않는다. 없는 경우에만 생성한다:
   `insert into storage.buckets (id, name, public, file_size_limit) values ('msgr', 'msgr', false, 26214400) on conflict (id) do nothing;`
   기존 버킷도 `public=false`·파일 크기 제한·`storage.objects` 조직/채널 접근 정책을 확인한다. `msgr-avatars` 공개 버킷과 프로필 정책은 아바타 마이그레이션이 생성한다.
3. **인증** — 회사 프로젝트의 Supabase Auth에서 Google·GitHub provider를 구성하고 Redirect URLs 허용 목록에 `http://127.0.0.1:*/auth/paired`를 등록한다. 웹 로그인도 사용하면 해당 서버의 `/auth/callback` 주소를 추가한다. 앱은 루프백 임시 포트로 OAuth를 돌려받는다.
4. **메신저에서 서버 지정** — 로그인 화면의 "서버"에 회사 프로젝트 URL과 공개 anon 키를 저장한다. 프로필은 해당 기기에만 저장되며 같은 배포 앱을 사용할 수 있다. 서비스 역할 키는 메신저 프로필에 넣지 않는다.
5. **에이전트 브리지(Argo 서버)는 재빌드 필요** — Argo의 `NEXT_PUBLIC_SUPABASE_URL`·`NEXT_PUBLIC_SUPABASE_ANON_KEY`는 **빌드 때 클라이언트와 인증 게이트에 인라인된다**. 기본 로컬 모드 타르볼을 설치한 뒤 `.env.local`만 바꾸거나 서버만 재시작해서 회사 서버로 전환할 수 없다. 해당 릴리스 소스에서 회사 프로젝트의 두 공개 env를 빌드 환경에 설정한 후 아래처럼 새 standalone과 타르볼을 만든다. env 값은 셸 이력·문서에 붙여넣지 말고 보호된 환경 파일/배포 설정으로 주입한다.

   ```bash
   npm ci
   ARGO_STANDALONE=1 npm run build
   node scripts/stage-server.mjs
   ```

   `stage-server.mjs`는 기존 standalone을 재사용하므로 앞의 빌드를 생략하지 않는다. 새 산출물을 설치하고 런타임에도 같은 프로젝트 공개 env를 설정한다. 각 에이전트 호스트에서 회사 프로젝트 계정으로 로그인하고 조직 소속·에이전트 파견 상태를 확인한다. 일반 에이전트 브리지는 해당 사용자의 기기 세션을 사용한다. `SUPABASE_SERVICE_ROLE_KEY`는 관리자 기능을 운영하는 신뢰된 서버에만 필요 시 설정하며, 데스크톱/메신저 빌드나 배포 타르볼에는 넣지 않는다.
6. **회사 노드(선택)** — 회사 에이전트를 두려면 조직 카드 "회사 노드"의 연결 코드로 `node scripts/msgr-node-bootstrap.mjs`를 회사 서버에서 한 번 실행한다.

확인: 무인증 `/api/me`가 401인지 → 로그인 → 조직 만들기 → 채널에 글 → 첨부 업로드 → 에이전트 파견 → 두 에이전트의 순차 멘션 답변과 종료까지 확인한다. 두 호스트가 연결된 경우에도 응답이 한 번씩만 생기고 원래 메신저 채널에 남아야 한다. 다른 조직/비공개 채널의 비회원 읽기·쓰기가 거절되는지도 별도 계정으로 확인한다.
데이터는 전부 회사 프로젝트에 평문으로 남는다([privacy-sync.md](privacy-sync.md) "팀 메신저").

### 팀 업무·자동화와 에이전트 브라우저

Argo 0.1.71과 Messenger 0.1.20의 팀 업무·자동화는 다음 순서로 갱신합니다.

1. 기존 메신저 마이그레이션을 적용한 DB에 `20260913010000_msgr_work_runs.sql`, `20260913110000_msgr_automations.sql`을 차례로 적용합니다. 기존 대화 기록을 삭제하지 않습니다.
2. 에이전트가 실행되는 각 기기의 Argo를 업데이트합니다. 새 실행기는 팀 업무 지원 상태를 알립니다. 구형 실행기는 일반 대화를 계속 사용할 수 있지만 팀 업무 후보에서는 제외됩니다.
3. Messenger를 업데이트하고 채널 상단 **업무**를 엽니다. **팀 업무**에서 목표와 완료 기준을 적으면 연결된 기존 에이전트 중 총괄을 선택하고 같은 채널에서 동료에게 일을 넘깁니다. 차단된 업무는 사유를 확인하고 보완 지시로 재개할 수 있습니다.

**자동화**에서는 담당 에이전트, 반복 주기, 시간대와 지시를 저장하고 일시정지·수정·삭제하거나 실행 기록을 확인합니다. 기록의 **담당자 응답 완료**는 담당 에이전트가 답했다는 뜻입니다. 이어지는 동료 업무 전체의 완료 판정은 아닙니다. 기기에서 실행되는 에이전트는 그 기기가 연결되어 있어야 하며, 오프라인이면 요청이 대기할 수 있습니다.

예약을 기기 연결과 무관하게 서버에서 접수하려면 서버 스케줄러도 설정합니다. `pg_cron`을 사용하는 관리자는 확장 설치 여부를 확인한 뒤 `scripts/sql/msgr-automation-scheduler.sql`을 적용합니다. 다른 스케줄러는 신뢰된 서버에서 서비스 역할로 `public.msgr_automation_dispatch_cloud()`를 매분 호출할 수 있습니다. 서비스 역할 키를 Messenger에 넣지 마세요. 서버 예약과 기기 예약은 같은 중복 방지 계약을 사용하며, 화면에는 실제 서버 스케줄러 작동 여부가 표시됩니다.

브라우저 작업에는 실행 기기의 Chrome·Chromium·Edge 등 지원 브라우저가 필요합니다. 회사·에이전트마다 별도 프로필을 사용하므로 다른 에이전트나 개인 브라우저의 로그인·쿠키를 가져오지 않습니다. 로그인 요청을 받으면 실행 기기에 열린 해당 에이전트의 창에서 필요한 계정만 연결하고 새 지시로 이어갑니다. 헤드리스 서버에서는 보이는 로그인 창을 제공하지 않으며, 모바일에서 원격 브라우저를 조작하는 기능은 포함하지 않습니다. Ego의 독립 프로필 소유를 확인할 수 없으면 전용 Chromium 프로필을 사용합니다.
